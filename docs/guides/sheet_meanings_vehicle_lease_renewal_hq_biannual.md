## 0. 先に結論（正本の一本化）

- `車両一覧`
  - 意味: 元台帳であり、同時に運用状態も保持する唯一の正本。
  - 主用途: 抽出元、最終反映先、運用列（`vehicleId` など）の保持。
- `車両（統合ビュー）`
  - 扱い: 廃止。現行実装では使用しない。

一本化の理由は、「抽出に使うシート」と「最終反映を確認するシート」を分けることで起きる同期漏れをなくすためです。

## 1. 全シートの役割マップ

| シート名 | 役割（何のためにあるか） | 主に更新するもの | 主な更新タイミング |
| --- | --- | --- | --- |
| `設定` | 通知先・期限・送信ON/OFFなど運用パラメータの定義 | 人手、`seedSettings` | 初期設定時、運用変更時 |
| `車両一覧` | 元台帳 + 運用正本（抽出と反映の基準） | 人手、`syncVehicles`、`applyMasterUpdates`、`seedE2EMockVehicles` | 日常更新、同期時、最終反映時、E2E準備 |
| `要入力` | 元台帳の不備検出ログ（満了日欠損など） | `syncVehicles` | 同期時 |
| `通知バッチ` | 半期便ごとの進行管理台帳（batch単位） | `createBiannualBatch`、各通知/反映関数 | 起票時、通知時、承認時、反映時 |
| `本部長副本部長確認_YYYYMMDD`（連番含む） | 回答と承認の入力面（業務UI） | `buildConfirmationSheet`、人手、`applyMasterUpdates` | シート生成時、回答/承認時、反映時 |

## 2. 各シートの意味（背景から）

### 2.1 `設定`

このシートは「コードを変えずに運用ルールを変える」ためにあります。
通知先や締切日をコード直書きにすると、運用変更のたびにデプロイが必要になり、障害リスクが上がるためです。

### 2.2 `車両一覧`

このシートは「事実データ」と「運用状態」を同じ行で管理する正本です。
- 事実データ: 契約満了日、管理部門、車種など
- 運用状態: `vehicleId`、`登録番号_結合`、`更新方針`、`一次回答`、`最終決定`、`完了フラグ` など

`syncVehicles` は別シート再生成ではなく、`車両一覧` の不足値補完と `要入力` 再生成を担います。

### 2.3 `要入力`

このシートは「不備の見える化」です。
`契約満了日なし`、`管理部門なし`、`登録番号不備` などを同期時に出力し、抽出漏れを防ぎます。

### 2.4 `通知バッチ`

このシートは「半期便の進行管理台帳」です。
1行が1バッチ（例: `2026H1`）を表し、対象期間、件数、送信時刻（初回通知、リマインド、専務依頼、村田主任通知）、ステータスを保持します。

### 2.5 `本部長副本部長確認_YYYYMMDD`（連番含む）

このシートは「人が判断を入力する業務画面」です。
`通知バッチ` の対象車両を展開し、本部回答、回答確認、専務判断、反映準備項目を入力します。

### 2.6 `通知ログ`

このシートは「通知処理の監査証跡」です。
成功だけでなく、未送信理由（未設定、条件未達、dry-run）も残します。

### 2.7 `テスト結果`

このシートは「自動テストの実行証跡」です。
`runTestSuite` の結果を蓄積し、`exportTestResults` で回収します。

## 3. データの流れ（どこからどこへ動くか）

1. `車両一覧` を入力・更新する
2. `syncVehicles` で `車両一覧` の `vehicleId` / `登録番号_結合` / `一次回答` を補完し、`要入力` を更新する
3. `createBiannualBatch` で `車両一覧` から対象を抽出し、`通知バッチ` を起票する
4. `buildConfirmationSheet` で `本部長副本部長確認_...` を生成する
5. 回答・承認入力後、`applyMasterUpdates` で `車両一覧` へ最終反映する
6. 通知処理の結果は `通知ログ` に残る

## 4. 運用上の注意

- `車両一覧` は正本なので、最終反映結果の確認先も `車両一覧` です。
- `syncVehicles` は `車両一覧` 編集連動（`onEditSourceSync`）と1時間ごとの定期実行で保険をかけます。
- 確認用シートが複数ある場合は、`通知バッチ.確認用シート名` に記録されたものを正として扱います。
- テスト後は `cleanupTestData` で `TEST` データを掃除し、次回テストの判定混入を防ぎます。
- 差戻し通知時は差戻し行の `本部回答`/`回答確認済み`/`村田主任確認済み`/`反映日時` がクリアされます。`専務判断`/`専務コメント`/`専務確認済み` はフィードバックとして保持され、本部回答の再入力時に自動クリアされます。承認済み行はそのまま残ります。
- 全件承認後は村田主任に通知が送られ、`通知バッチ.村田主任通知送信日時` に記録されます。

## 5. シート別の権限と目的（全シート）

| シート名 | 誰が触ってよいか | 触る目的 | 触ってはいけないこと |
| --- | --- | --- | --- |
| `設定` | 編集責任者: 運用管理者。入力担当: 開発者（テスト時のみ） | 通知先、期限、送信ON/OFFなど運用条件を設定する | 通常運用でテスト値を残す、キー名を変更する |
| `車両一覧` | 編集責任者: 台帳管理担当（原本管理者）+ システム（同期/反映） | 事実データの更新と運用列の整合維持 | `vehicleId` / `登録番号_結合` / 運用列を手作業で壊す |
| `要入力` | 編集責任者: システム（GAS）。閲覧担当: 台帳管理担当 | 欠損や不備を検出して、元台帳の修正対象を示す | 不備をこのシート上で「修正済み」にしない（修正は `車両一覧` で行う） |
| `通知バッチ` | 編集責任者: システム（GAS）。閲覧担当: 運用担当 | 半期便の進捗（対象件数、送信時刻、ステータス）を管理する | `batchId`、送信時刻、ステータスを手編集する |
| `本部長副本部長確認_YYYYMMDD`（連番含む） | 入力担当: 本部長・副本部長（`本部回答`/`回答確認済み`）、専務（`専務判断`/`専務コメント`）、村田主任（反映前必須項目）。編集責任者: 運用担当（シート選定） | 一次回答、承認、反映前入力を1画面で完了させる | 担当外列の編集、`vehicleId`/`batchId` の書き換え |
| `通知ログ` | 編集責任者: システム（GAS）。閲覧担当: 運用担当 | 通知成功/失敗/スキップ理由の監査証跡を残す | ログの手修正・削除で監査性を失うこと |
| `テスト結果` | 編集責任者: システム（GAS）。入力担当: 開発者（テスト実行時） | テストの実行結果を記録し、受け入れ条件の達成を確認する | 本番運用の判断材料として古い結果を混在させる |

## 6. 補足（保護と制約）

- `要入力` はシート保護の対象です。
- 確認用シートの `専務判断` / `専務コメント` は範囲保護の対象です。
- `車両一覧` は人手編集シートでもあるため、全面保護ではなく運用規約で整合を守ります。
